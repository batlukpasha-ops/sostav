# Передача контекста: дипломная платформа формирования команд

Дата подготовки: 16 октября 2026 года. Документ предназначен для новой задачи Codex, в том числе при продолжении работы в браузере.

## 1. Главное для нового Codex

Проект называется `dating-service` по историческим причинам. Сейчас это небольшой учебный Dating Service на FastAPI и PostgreSQL, но **новая предметная область — веб-платформа для формирования команд для стартапов и IT-проектов**. Рабочее название интерфейса — «Состав».

Пользователь — Павел, начинающий backend-разработчик. Он делает диплом и хочет учиться в процессе разработки. Codex должен помогать как наставник: объяснять решения, давать небольшие самостоятельные задачи, проверять код и помогать исправлять ошибки. Не нужно автоматически писать за него весь проект.

Последняя содержательная просьба по продукту: **сделать каркас всех планируемых страниц, а визуальный дизайн доработать позже**. Сохранился HTML-прототип с 26 экранами и состояниями. Он ещё не является работающим веб-приложением и не подключён к backend.

На момент передачи:

- концепция продукта переработана в обсуждениях;
- одна страница проекта оформлена в Figma;
- общий каркас сохранён отдельно в HTML;
- код backend всё ещё относится к сервису знакомств;
- миграция на новую предметную область не начата.

**Первый шаг в новой задаче — изучить этот документ и прототип, проверить комплектность каркаса и предложить один небольшой следующий шаг. Пока не переписывать backend, не проектировать сразу всю БД и не создавать десятки файлов.**

## 2. Тема и требования диплома

Содержательная тема: разработка веб-платформы, которая помогает специалистам находить проекты, а авторам стартапов и IT-проектов — собирать команды на конкретные роли.

Это описание концепции из обсуждений. Официальная утверждённая формулировка темы, методичка вуза, требования к пояснительной записке, обязательные главы, сроки и критерии защиты в просмотренных материалах не найдены. Не выдавать рабочую формулировку за дословную тему из задания на диплом.

Планируемые возможности итогового проекта:

1. Пользователи и профили специалистов.
2. Навыки и уровни владения ими.
3. Опыт, учебные работы и портфолио.
4. Проекты и открытые роли в их командах.
5. Требования к каждой роли.
6. Поиск кандидатов для автора и подходящих проектов/ролей для специалиста.
7. Объяснимый рейтинг совместимости.
8. Отклики специалистов на роли.
9. Приглашения от авторов проектов.
10. Принятие и отклонение предложений.
11. Формирование команды после согласования участия.
12. Полноценный веб-интерфейс, а не только Swagger и backend API.
13. Личная переписка и собственный видеозвонок один на один внутри сайта — добавлены позднее по прямому желанию пользователя.

В раннем расширенном описании также фигурировали интересы, желаемые направления/роли, формат участия и доступное время пользователя; направление и стадия проекта; обязательные и желательные навыки роли, минимальные уровни, опыт, формат работы и занятость. Это требования расширенной концепции, а не уже реализованные поля.

### Подбор и совместимость

В расширенной задумке это существенная особенность диплома, а не случайная рекомендация:

- подбор в обе стороны: кандидаты для роли и роли/проекты для специалиста;
- сначала проверка обязательных условий: навыки, достаточный уровень, формат участия, доступность и другие обязательные требования;
- затем оценка подходящих вариантов по дополнительным критериям: желательные навыки, опыт, интересы и т. п.;
- возможны разные веса критериев;
- пользователь должен видеть, почему получена рекомендация: совпавшие условия и итоговая оценка.

Формула, веса, шкала уровней, способ проверки навыков и способ оценки качества подбора ещё не утверждены. Упоминавшийся пример «82% соответствия» был иллюстрацией, а не определённой формулой.

В дальнейшем ради выполнимого первого MVP решили начать с ручного поиска и формирования команды, а подбор и уровни навыков отложить. **Отложить из первого этапа не означает исключить из диплома.** Перед планированием итогового объёма нужно сверить это с официальными требованиями преподавателя.

## 3. Формат совместной работы

Правила прямо сформулированы пользователем в предыдущей задаче:

- Не писать большие готовые части без прямой просьбы.
- Не создавать сразу целые модули, архитектуру или десятки файлов.
- Сначала объяснять, что делаем и зачем это пользователю.
- Давать возможность попробовать самому, если задача подходит для самостоятельной работы.
- Делать code review: указывать ошибку, объяснять причину и способ исправления.
- Объяснять простым языком на примерах этого проекта.
- Небольшие примеры допустимы, но не должны заменять самостоятельную реализацию.
- Если есть несколько способов, объяснять их преимущества и ограничения.
- Не усложнять архитектуру и не добавлять технологии ради самих технологий.
- Каждое архитектурное решение Павел должен уметь объяснить на защите.

Обычный цикл: небольшая задача → объяснение → попытка Павла → ревью и помощь → проверка → следующий шаг.

Это не запрет на выполнение прямых поручений. Позднее пользователь отдельно попросил Codex сделать готовый дизайн страницы, а затем каркас всех страниц. Эти поручения разрешали работу над макетами, но не означали просьбу автоматически написать весь backend.

Computer Use в предыдущем обсуждении решили пока не использовать. Для Figma применяли подключение Figma; Павел также мог выполнять действия самостоятельно с объяснениями.

## 4. Принятые продуктовые решения

### Пользователи, проекты и роли

- Один аккаунт может одновременно искать проекты и создавать собственные. Постоянное разделение на отдельные типы аккаунта «автор» и «специалист» не требуется.
- После регистрации предусмотрена форма первоначального заполнения профиля, затем каталог проектов.
- Для начала не нужно заставлять автора идеи изображать технического специалиста: подробные навыки и портфолио можно заполнить позднее.
- Профиль: имя, специализация, описание, навыки, опыт/учебные проекты, ссылки на работы.
- Проект: название, краткое и подробное описание, цель первой версии, автор, открытые роли и команда.
- Роль — конкретное место в команде с названием, задачами, навыками и требованиями.
- Для первого MVP **одна роль = одно место**. Если нужны два backend-разработчика, создаются две роли. Количество мест в одной роли отложено.
- Названия ролей задаёт автор; дизайнер, backend и frontend — примеры, а не закрытый список специализаций.

### Отклик, приглашение и участие

- Отклик всегда связан с конкретной ролью конкретного проекта.
- Специалист отправляет короткое сообщение; автор видит его профиль. Ссылка на работы может быть необязательной.
- Решение по отклику принимает автор проекта.
- Приглашение тоже связано с конкретной ролью; автор выбирает свой проект и открытую роль, пишет сообщение.
- Решение по приглашению принимает приглашённый специалист.
- Отправка отклика или приглашения ещё не означает вступление в команду.
- Принятие отклика автором или приглашения специалистом создаёт участие; дополнительное повторное подтверждение пока не предусмотрено.
- После принятия место занято, роль перестаёт быть открытой.
- Отклонение сохраняется в истории и не создаёт участие.
- Базовые состояния предложений: ожидает решения, принято, отклонено.

Точные правила повторных заявок, отзыва, истечения срока, конкурирующих приглашений и нескольких претендентов на одно место ещё требуют проработки. Прототип не заменяет эти правила backend.

### Чат и видеозвонок

- Переписка становится доступна после отправки отклика или приглашения: у общения есть контекст проекта и роли.
- Обсудить условия можно до принятия решения об участии.
- Общение и созвон необязательны.
- Созвон сам по себе не добавляет человека в команду и не принимает заявку.
- Пользователь выбрал собственный видеозвонок один на один с камерой и микрофоном внутри сайта.
- Экран переписки: список диалогов слева; сообщения, собеседник, проект/роль и кнопка звонка справа.
- Вызов: принять или отклонить; во время разговора — видео собеседника, своё видео, переключатели камеры/микрофона и завершение.
- После завершения возврат к переписке.
- Планировать реализацию постепенно: основной подбор команды → текстовый чат → встроенные видеозвонки. В последней принятой формулировке назначение времени встречи добавляется после работающих звонков.
- В прототип уже включён экран назначения созвона; его наличие не означает, что эта функция реализована или должна делаться раньше самих звонков.

Технически обсуждался WebRTC, обмен сигналами установления соединения и возможная потребность в STUN/TURN. Конкретные серверы, библиотеки, протокол хранения/доставки сообщений и инфраструктура не выбраны. Групповые звонки, запись и демонстрация экрана не входят в первую версию.

### Универсальное оформление проекта

- Общие меню, шрифты, цвета, кнопки, карточки и расположение блоков принадлежат платформе.
- Автор задаёт название, описание, обложку и роли своего проекта.
- Индивидуальных тем, настройки шрифтов/цветов и перестройки страницы автором в MVP нет.
- Обложка необязательна. Если её нет — нейтральная область с первой буквой названия.
- Изображение занимает выделенную область; название и описание остаются отдельным читаемым текстом.
- Предусмотрены замена и удаление обложки.

**«ВелоГород» — пример проекта, размещённого внутри платформы. Мы не разрабатываем сервис аренды велосипедов.** Велосипед — пример обложки автора, а не универсальный логотип всех проектов.

## 5. Объём и этапы

### Первый рабочий MVP

Регистрация/вход, профили, проекты, роли, каталоги и простой поиск/фильтры, отклики, приглашения, решения и команда, базовый веб-интерфейс.

Основные пути:

1. Специалист: регистрация → профиль → каталог → проект → роль → отклик → решение → участие.
2. Автор: создать проект → добавить роли → опубликовать → посмотреть отклики → изучить кандидата → принять → команда.
3. Приглашение: каталог специалистов → профиль → выбрать свой проект и роль → отправить приглашение → ответ специалиста → участие.
4. После появления общения: отклик/приглашение → при необходимости чат и созвон → отдельное решение об участии.

### Последующие этапы

- Переписка, затем встроенные звонки и назначение встречи.
- Объяснимый подбор и рейтинг совместимости; порядок относительно общения нужно сверить с приоритетами диплома.
- Уровни навыков и более структурированные требования.

Из первой версии исключены платежи, монетизация, лента активности, подписки, репутация и отзывы, управление задачами/документами команды, сложная аналитика, несколько владельцев с развитой системой прав, групповые видеоконференции, запись звонков и демонстрация экрана. Email/push-уведомления отложены; сначала достаточно состояний внутри сайта.

### Реализованные API-операции

| Метод и путь | Поведение |
| --- | --- |
| `POST /users` | Имя, email, возраст; создание пользователя. Дублирующий email обрабатывается как 400. |

## 9. Запуск и перенос в облачную задачу

В новой среде потребуется Python и доступный PostgreSQL. Старый код умеет брать параметры подключения из `DATABASE_URL` или `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`.

Общий порядок: создать виртуальное окружение → установить `requirements.txt` → настроить окружение БД → подготовить отдельную базу → инициализировать её → запустить `uvicorn main:app --reload`. Swagger находится по `/docs`, обычно `http://127.0.0.1:8000/docs`.

**Не запускать `schema.sql` на существующей базе без разбора: он начинает с удаления таблиц.** Для новой временной среды допустима отдельная пустая база. Это конкретное свойство текущего файла, а не готовый план миграции.

Статус локального PostgreSQL, его данные, версия Python и фактический запуск API в задаче подготовки передачи не проверялись. README упоминает PostgreSQL 18 на Windows как пример команды; это не гарантия установленной версии в облаке.

## 11. Конкретный следующий шаг

**Завершить проверку общего каркаса до начала серьёзной переделки backend.**

Новый Codex сначала читает передачу, README и прототип, затем кратко подтверждает текущую концепцию и показывает один сценарий: **каталог проектов → страница «ВелоГород» → роль → отклик → состояние «ожидает решения»**. Дальше проверяет сторону автора: **профиль кандидата → принятие → участник в команде и занятое место**. Отдельно проверяет приглашение: решение принимает специалист.

Критерии готовности каркаса к следующему этапу:

- на каждом шаге ясно, кто действует, в каком проекте и на какую роль;
- отправка, переписка и созвон не создают участие;
- принятие меняет состояние заявки, команды и роли согласованно;
- данные разных проектов не смешиваются;
- отказ не создаёт участие;
- последующие функции обозначены как последующие;
- прототип не выдаётся за готовый backend.

После такой проверки вместе выбрать небольшую учебную задачу для перехода к backend. Не переписывать весь проект одним действием.
